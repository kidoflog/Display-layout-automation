## 作業時の前提

- **レビューはコードの読解に基づく。** アプリは起動しておらず、実機での再現は行っていない。計算部分の `LayoutChecks` だけは実行し、全項目が通っている。
- **仕様の正は要件定義書。** 〔確定〕の項目は変えない。〔提案〕〔要検証〕の項目を変える場合は、要件定義書と実装の決定事項も合わせて更新する。
- **変更してはならない挙動**：主画面の位置、各画面のX座標、解像度・表示倍率・回転を変えないこと。測定中は実際の配置を変えないこと。確定前の配置を自動復元の対象として保存しないこと。
- **画面配置APIを呼ぶコードは実機でしか確認できない。** 実機確認ができない変更は、その旨を `implementation-decisions.md` の「保留・実機検証」に追記する。
- **計算やロジックを変えたら `Checks/main.swift` に検査を足す。** 純粋なロジックは `DisplayHeightCore` に置くと検査できる。

### このMacでのビルド方法

`swift build` と `swift run` は現在使えない（Issue 1）。それまでは `swiftc` を直接使う。

```sh
export SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX15.4.sdk
export CLANG_MODULE_CACHE_PATH="${TMPDIR:-/tmp}/displayheight-clang-cache"
OUT="${TMPDIR:-/tmp}/displayheight-check" && mkdir -p "$OUT" && cd "$OUT"
REPO=/Users/kaoru/ai_sandbox/display_automation_layout

# 計算部分のモジュールと検査
swiftc -swift-version 6 -parse-as-library -emit-module -emit-library \
  -module-name DisplayHeightCore "$REPO/Sources/DisplayHeightCore/Layout.swift"
swiftc -swift-version 6 -I . -L . -lDisplayHeightCore "$REPO/Checks/main.swift" -o checks
./checks    # 「LayoutChecks: all checks passed」が出れば成功

# アプリ本体の型検査
swiftc -swift-version 6 -typecheck -I . "$REPO"/Sources/DisplayHeight/*.swift
```

既定のSDK（MacOSX27.0）はコンパイラ（Swift 6.3.3）と版が合わず使えない。MacOSX15.4.sdk を指定すると通る。

## Issue 1：SwiftPMが起動せず、ビルド手順が動かない

**優先度**：高　**種別**：環境・スクリプト

**現象**
`swift run --disable-sandbox LayoutChecks` と `swift build` が、コンパイルの前に次のエラーで終了する。

```text
dyld: Symbol not found: _$s19BuildServerProtocol019SourceKitInitialize...
  Referenced from: /Library/Developer/CommandLineTools/usr/bin/swift-package
  Expected in: /Library/Developer/CommandLineTools/usr/lib/swift/pm/BuildServerProtocol.framework/...
```

READMEの検証コマンドと `scripts/build-app.sh` が、このMacでは実行できない。

**原因**
Command Line Tools内の `swift-package` と付属フレームワークの版が合っていないとみられる。コードの問題ではない。加えて、既定のSDK（MacOSX27.0）がコンパイラ（Swift 6.3.3）より新しく、`swiftc` 単体でもSDKを指定しないと失敗する。

**該当箇所**
- `scripts/build-app.sh` 8〜14行目：`MacOSX15.4.sdk` を決め打ちし、`swift build` に依存している。
- `README.md` 「ビルドと検証」。

**対応方針**
1. 根本対応はCommand Line Toolsの入れ直し。これは依頼者の作業で、管理者権限が要る。コードからは直せない。
2. それまでの回避策として、`swift build` が失敗したら `swiftc` を直接使ってアプリを組み立てる経路を `build-app.sh` に足す。上の「このMacでのビルド方法」と同じ手順で、型検査の代わりに実行ファイルを出力する。
3. 検査を実行するスクリプト（例：`scripts/run-checks.sh`）を足し、READMEの手順を更新する。

**完了条件**
- このMacで、スクリプト1本で `LayoutChecks` が実行でき、「all checks passed」が出る。
- このMacで `bash scripts/build-app.sh` が `.build/DisplayHeight.app` を作る。
- SwiftPMが正常な環境では、従来どおり `swift build` を使う。
- READMEの手順が実際に動くものと一致している。

**要件との差**

**対応方針**

- 上げたあとも次が成り立つことを確認する。
  - Escで測定を中止できる（オーバーレイがキーウィンドウになる）。
  - 画面上端・下端付近でも線が指定でき、案内文が読める。案内文は現在、上端から28ポイントの位置に描いている（83行目）。
- 全画面表示のアプリがある状態での動作は要件9で〔要検証〕。実機確認ができなければ保留事項に残す。

**完了条件**
- 測定中、メニューバーとDockの領域でも押下・ドラッグ・リリースで高さを指定できる。
- 測定中のクリックで、メニューバー、Dock、背後のアプリが反応しない。
- Escでの中止が従来どおり動く。

## Issue 3：保存ファイルが壊れると以後の保存がすべて失敗する

**優先度**：高　**種別**：不具合　**要件**：6.1、6.2

**現象**
`profiles.json` 全体がJSONとして読めなくなると、確定のたびに「macOSには配置を保存しましたが、アプリ側の保存に失敗しました。」となる。自動復元用の保存が二度と更新されない。保存形式を将来変えた場合も同じ状態になる。

**原因**
`Sources/DisplayHeight/ProfileStore.swift` 31〜37行目の `save` が、最初に `load()` を呼ぶ。`load()` は25行目のデコードに失敗すると例外を投げ、`save` もそこで終わる。

READMEの「不正な保存プロファイルを読み飛ばし」は、26〜28行目の項目単位の除外を指している。ファイル全体が読めない場合は対象外になっている。

**対応方針**
- `save` では、既存ファイルが読めないことを理由に保存を失敗させない。
- 読めないファイルは上書きで消さず、別名で退避する（例：`profiles.corrupt-<日時>.json`）。そのうえで空の状態から保存する。
- `load` 側（自動復元の照合）は、読めない場合に「保存配置なし」として扱う現在の動作（`main.swift` 483行目の `try?`）を維持する。
- 項目単位の除外（キーの不一致、`LayoutPlanner.sequence` が通らない配置）は維持する。

**完了条件**
- `profiles.json` を不正な内容にした状態で確定しても、保存が成功する。
- 元の不正なファイルが退避されて残る。
- 正常なファイルでは、既存の他構成のプロファイルが保存後も残る。
- ファイルの読み書きを差し替え可能にするなどして、上の2点を検査で確認できれば望ましい。

## Issue 4：ウィンドウを閉じるとアプリが終了し、自動復元が働かなくなる

**優先度**：中　**種別**：設計　**要件**：7.1　**着手前に依頼者へ確認**

**現象**
- 操作ウィンドウを閉じるとアプリが終了する。自動復元はアプリ起動中しか働かないため、ウィンドウを開いたままにする必要がある。
- ログイン時起動を有効にすると、ログインのたびにウィンドウが前面に出る。

**原因**
- `Sources/DisplayHeight/main.swift` 81〜84行目：`windowShouldClose` が `NSApp.terminate` を呼ぶ。
- 122〜123行目：起動時に必ずウィンドウを表示し、アプリを前面にする。
- 509行目：`.regular` で起動し、常駐の手段（メニューバー項目など）がない。

**判断が必要な点**
常駐の形をどうするか。候補は次のとおり。

- A：メニューバー項目を足し、ウィンドウを閉じても終了しない。終了はメニューから行う。**推奨。** 要件7.1の「アプリ起動中に再接続を検知」と相性がよい。
- B：ウィンドウを閉じたら隠すだけにし、Dockのアイコンから再表示する。変更は小さいが、終了方法が分かりにくい。

**完了条件（Aの場合）**
- ウィンドウを閉じてもアプリが動き続け、再接続時の自動復元が働く。
- メニューバーからウィンドウの再表示と終了ができる。
- ログイン時の起動ではウィンドウを前面に出さない。自動復元の確認が必要なときだけ表示する。
- 確認中に終了した場合に仮適用前へ戻す動作（要件6.1）が維持される。
- 要件定義書と実装の決定事項に常駐の形を追記する。

## Issue 5：操作中に起きた再接続では自動復元が行われない

**優先度**：中　**種別**：不具合　**要件**：7.1、8

**現象**
測定中や確認中に画面を抜き差しすると、操作は正しく取り消される。しかし、その新しい構成に保存配置があっても自動復元が行われない。次に構成が変わるまで再判定されない。

**原因**
`Sources/DisplayHeight/main.swift` の `checkReconnection`（451行目〜）。

- 465行目で `connectionTracker.observe` を呼び、「構成が変わった」という判定をその場で消費する。
- 466〜480行目で測定中・確認中・適用中なら `cancelSession` して `return` する。
- この時点で `lastTopology` は新しい構成になっているため、次回の `observe` は「変化なし」を返す。

**対応方針**
- 操作の取り消しで `return` したあと、待機状態に戻ってからもう一度照合する。例：取り消し後に `scheduleReconnectionCheck(force: true)` を呼ぶ。
- 確認中・適用中の取り消しでは、`cancelSession` が取り消した構成を `connectionTracker.cancel` に記録する（353〜356行目）。同じ構成のまま取り消した場合に復元を繰り返さない動作（要件7.1）は維持する。
- 判定の順序は `ConnectionTracker`（`Sources/DisplayHeightCore/Layout.swift` 223〜241行目）に寄せると検査しやすい。

**完了条件**
- 測定中に構成が変わり、新しい構成に保存配置がある場合、測定の中止後に自動仮適用が始まる。
- 確認中にユーザーが取り消した場合、同じ構成のままでは自動仮適用が再び始まらない。
- 上の2点に相当する検査を `Checks/main.swift` に足す。

## Issue 6：対象外画面があるときの案内が誤っている

**優先度**：中　**種別**：不具合　**要件**：8

**現象**
Sidecar、AirPlay、ミラーリング、判別できない外部画面が接続されていると、自動復元の照合が3回再試行される。そのあと「画面構成が安定せず、自動復元を見送りました。」と表示される。実際の理由（対象外の画面がある）が伝わらない。

**原因**
`Sources/DisplayHeight/main.swift` 485〜494行目。`try? DisplaySystem.snapshot()` で失敗理由を捨てている。「対象外の画面がある」場合と「構成の読み直しが一致しない（まだ安定していない）」場合を同じ分岐で扱っている。

**要件との差**
要件8「対象外の画面や判別不能な画面が接続されている：初版では操作全体を見送り、理由を案内する」。

**対応方針**
- `snapshot()` が例外を投げた場合は再試行せず、そのエラーの説明を表示して見送る。
- 再試行するのは、`snapshot()` は成功したが `sameLayout` が一致しない場合だけにする。
- `NSScreen` との対応付けの失敗（`DisplaySystem.swift` 69〜73行目）は、再接続直後に一時的に起きうる。これは再試行の対象に残す。エラーの種類を分けて区別する。

**完了条件**
- 対象外画面がある状態では、再試行せずに対象外である理由が表示される。
- 構成が安定していないだけの場合は、従来どおり最大3回再試行する。

## Issue 7：許容差の判定が正常な結果を失敗にすることがある

**優先度**：中　**種別**：不具合　**要件**：5.2

**現象**
仮適用後の検証で、位置の判定は通るのに「指定した点の高さが一致しませんでした。」となって取り消されることがある。

**原因**
`Sources/DisplayHeight/main.swift` の `verifyPreview`。

- 241〜245行目：各画面の実際のYが予定位置から1単位以内なら通す。
- 246〜254行目：各組の指定点の高さの差が1単位以内でなければ失敗にする。

予定位置は整数に丸めるため、指定点の差には最大0.5のずれが最初から含まれる（`Layout.swift` 112行目）。macOSの補正で対象画面が1単位ずれると、差は最大1.5になる。基準画面も逆方向にずれると、さらに広がる。位置の判定が許す範囲を、高さの判定が許していない。

**判断の材料**
要件5.2は「各組につき配置座標の1単位以内を暫定基準」とし、端数処理を含む最終値は実機検証で確定するとしている。次のどちらかにそろえる。

- A：位置の判定を厳しくする（予定位置との完全一致を求める）。高さの差は丸めによる0.5以内に収まる。**推奨。** 許容差の意味が要件どおりになる。macOSが1単位でも補正したら取り消す動作になる。
- B：高さの判定の許容差を、丸め分を含めた値に広げる。要件5.2の数値を更新する必要がある。

**完了条件**
- 位置の判定を通った結果が、高さの判定で落ちることがない。
- 判定を `DisplayHeightCore` に移し、境界値（丸め0.5、補正1単位）の検査を足す。
- 採用した基準を要件5.2と実装の決定事項に反映する。
- 同じ「1単位以内」の比較が `confirm`（316、326行目）と `rollback`（405、414行目）にもある。基準を変える場合はそろえる。

## Issue 8：要件6.2の保存内容の一部が未実装

**優先度**：中　**種別**：仕様との差　**要件**：6.1、6.2、8　**着手前に依頼者へ確認**

**現象**
要件6.2は保存内容に「変更前の配置と、確定済み／未確定を区別する情報」を含めている。実装が保存するのは、確定した配置と保存日時だけ（`ProfileStore.swift` 4〜9行目）。変更前の配置はメモリ上にしかない。

**現在の動作**
仮適用は `.forAppOnly` で行う（`DisplaySystem.swift` 124〜125行目）。この指定では、アプリが終了するとmacOSが配置を元に戻す。強制終了時の復帰はこの仕組みに頼っている。実機では未確認（要件8で〔要検証〕）。

**判断が必要な点**
- A：仕様を実装に合わせる。「未確定の配置は `.forAppOnly` で適用し、アプリ終了時の復帰はmacOSに任せる。変更前の配置は保存しない」と要件6.2に書く。強制終了時の実機確認を保留事項に残す。**推奨。** 追加のコードが不要で、未確定の情報をファイルに残さない。
- B：実装を仕様に合わせる。仮適用の前に変更前の配置と「未確定」の印を保存し、起動時に印が残っていれば元の配置へ戻す。強制終了後にmacOSが戻さなかった場合にも対応できる。

**完了条件**
- 要件定義書6.2と実装が一致している。
- Bの場合：仮適用中に強制終了しても、次回の起動時に変更前の配置へ戻る。確定または取り消しのあとは印が消える。

## Issue 9：待機中のEscで「変更を取り消しました。」と表示される

**優先度**：低　**種別**：不具合

**現象**
何も操作していない待機状態でEscを押すと、「変更を取り消しました。」と表示される。

**原因**

## Issue 13：`swiftc` 経由のビルドがmacOS 26未満で起動できない

**優先度**：中　**種別**：スクリプト　**追加日**：2026-10-02

**現象**
SwiftPMが使えない環境で `scripts/build-app.sh` が作る実行ファイルは、最低対応OSがmacOS 26.0になる。`Info.plist` の `LSMinimumSystemVersion` は13.0で、食い違っている。macOS 13〜25では起動できない。最適化も付いていない。

確認方法：

```sh
otool -l .build/DisplayHeight.app/Contents/MacOS/DisplayHeight | grep -A4 LC_BUILD_VERSION

```

**原因**
`scripts/build-app.sh` 23行目と28行目の `swiftc` に対応OSの指定がない。指定がないと、ビルドしたMacのOS版が最低対応OSになる。SwiftPM経由のビルドは `Package.swift` の `.macOS(.v13)` と `-c release` を使うため、この問題は起きない。

- `scripts/run-checks.sh` の `swiftc` は手元で実行するだけなので、変更は不要。

**完了条件**
- `swiftc` 経由で作ったアプリ本体と `libDisplayHeightCore.dylib` の両方で、`otool -l` の `minos` が13.0になる。

## Issue 14：測定中に配置を手動で変えると自動仮適用が始まる

**優先度**：中　**種別**：不具合　**要件**：7.2　**追加日**：2026-10-02

**現象**
測定中に、ユーザーがシステム設定で画面の位置だけを変える。測定は正しく中止されるが、続けて保存配置の自動仮適用が始まり、確認画面が出る。画面の組み合わせは変わっていない。放置すれば10秒で元に戻る。

**原因**

**対応方針**

**完了条件**
- 測定中に位置だけが変わった場合、測定は中止され、自動仮適用は始まらない。
- 測定中に画面の組み合わせが変わり、新しい構成に保存配置がある場合は、従来どおり自動仮適用が始まる（Issue 5の動作を保つ）。

## Issue 15：ログイン時起動が有効だと手動起動でもウィンドウが出ない

## Issue 16：Issue 15の修正が効かず、ログインによる起動でもウィンドウが出る

**優先度**：中　**種別**：不具合　**要件**：7.1　**追加日**：2026-10-05

**現象**
起動方法によらず、起動の約1秒後に操作ウィンドウが表示される。ログインによる起動でも表示される。手動起動でウィンドウが出ない問題（Issue 15）は解消したが、要件7.1の「ログインによる起動時には操作ウィンドウを前面に出さず」を満たさなくなった。

**原因**
起動イベント（open-application）を受け取る処理の登録が遅く、一度も呼ばれない。

- `Sources/DisplayHeight/main.swift` 69〜72行目は、`applicationDidFinishLaunching` の中で `NSAppleEventManager` に受け取りを登録している。
- このイベントは、`applicationDidFinishLaunching` が呼ばれる時点ですでに処理中になっている。あとから登録した処理には届かない。
- そのため `handleOpenApplicationEvent`（114〜120行目）は呼ばれず、`receivedOpenEvent` は常に `false` のままになる。
- 73〜77行目の予備の処理（1秒後にイベントが来ていなければウィンドウを出す）が毎回動く。

**確認した方法**
同じ登録方法の検証用アプリを作り、`open` で起動した。結果は次のとおり。

- `applicationDidFinishLaunching` の中で登録した処理は呼ばれなかった。
- `applicationDidFinishLaunching` の中で `NSAppleEventManager.shared().currentAppleEvent` を読むと、起動イベント（`kAEOpenApplication`）が取れた。

DisplayHeight本体を起動しての確認は行っていない。

**対応方針**
- 受け取りの登録（69〜72行目）、1秒後の予備の処理（73〜77行目）、`handleOpenApplicationEvent`、`receivedOpenEvent`、終了時の登録解除（`applicationWillTerminate` 内の `removeEventHandler`）を削除する。
- `applicationDidFinishLaunching` の中で `NSAppleEventManager.shared().currentAppleEvent` を直接読む。
  - イベントが起動イベントで、`keyAEPropData` の値が `keyAELaunchedAsLogInItem` なら、ウィンドウを表示しない。
  - それ以外（印がない、イベントが取れない）は、ウィンドウを表示する。
- 判定は関数に切り出し、起動直後に1回だけ呼ぶ。待ち時間は入れない。

**実機確認が必要な点**
`SMAppService.mainApp` で登録したログイン起動に、`keyAELaunchedAsLogInItem` の印が付くかどうかは未確認。確認には、ログイン時起動を有効にしてログインし直す必要がある。印が付かない場合、この方法ではログイン起動を判定できない。その場合は別の手段を検討し、決まるまでは `implementation-decisions.md` の「保留・実機検証」に残す。

**完了条件**
- 手動起動（Finder、`open`、実行ファイルの直接起動）では、待ち時間なしで操作ウィンドウが表示される。
- 起動イベントにログイン項目の印がある場合、操作ウィンドウが表示されない。
- ログインによる起動でも、自動復元の確認が必要なときはウィンドウが表示される。
- 実際のログインでの動作を確認する。確認できなければ、未確認であることを `implementation-decisions.md` に明記する。現在の記述（2026-10-05の項）は、実装の変更に合わせて書き直す。
